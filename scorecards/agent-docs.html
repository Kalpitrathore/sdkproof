One sentence fixes what a library's full documentation does not.

Across three libraries, a single sentence naming a breaking change fixes the failure it names, nine or ten times out of ten. Two of those libraries ship the same sentence inside their own larger documentation, and there it fixes nothing. Why is genuinely unclear — the obvious explanation was tested and did not hold.

What is measured

Three libraries, each with one task an AI assistant reliably gets wrong, and each with a sentence in its own documentation that names the fix. Ten trials per cell. The only thing that changes is how that sentence reaches the model.

The one thing that holds across all three: the sentence works. These are not corrections written for the experiment — every one is quoted verbatim from the library's own documentation. The model reads the instruction and follows it.

The obvious explanation, and why it is wrong

Two of three libraries fail when the same sentence sits inside a 25 KB document. The natural reading is that volume buries it — React Router's sentence is at line 182 of a 213-line file, and there it never works.

So that was tested directly. One library, one task, one sentence, and nothing varying but the amount of surrounding text and where the sentence sits in it. The padding is real Next.js documentation for unrelated APIs, checked to make sure it never states the signature being tested:

Neither size nor position reproduced the failure. The instruction survived being buried at the end of 25 KB and survived 50 KB of padding. Whatever stops it working inside React Router's and Prisma's own packs, it is not simply that those packs are long.

The live hypothesis, untested: the padding used here is topically distant — headers, redirect, link, image. The documentation that did smother the correction was densely about the same API surface, full of adjacent guidance competing for the same decision. Competing content, rather than volume, would explain all three results — and it has not been measured. Until it is, this page does not claim a cause.

A confound worth stating

The three failures are not equally hard to correct. Next.js's is an arity error — "the second argument is required" is about as direct as a fix gets. React Router's is a field rename inside a destructured argument. It is entirely possible that some corrections are robust to their surroundings and others are fragile, and that this explains the table above better than anything about the documents.

What can be said, and what cannot

Supported: a short, specific sentence naming a breaking change fixes the failure it names, on all three libraries measured, 9–10 times out of ten. It is worth shipping one.

Supported: two of these three libraries already contain that sentence somewhere in their own documentation, and it is not reaching the model there.

Not supported: that document length is the cause. That was the earlier conclusion on this page and the controlled test did not reproduce it.

Sizes span 2,217 characters to 5,673,960 under two filenames that promise the same thing. A model with no ability to fetch gets nothing usable from a link index, and nothing at all from a five-megabyte bundle. Next.js is worth copying on one point regardless of the above: it serves a Markdown version alongside every docs page — 6.6 KB where the HTML is 490 KB — and that file fixed its failure ten times out of ten.

Limits

One model (Claude Opus 5), three libraries, one failing task each, ten trials per cell, one-shot prompts rather than an agent that can search. The single-sentence arm is close to handing the model the answer — its entire context is the correction — so it measures whether a salient instruction is followed, not whether documentation works in normal use.
