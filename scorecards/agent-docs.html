Measurement · 7 August 2026

A library's own docs bury its own correction.

Across three libraries, a single sentence naming a breaking change fixes the failure it names, ten times out of ten. Two of those libraries ship the same sentence inside their own larger documentation, and there it fixes nothing. It is not the length. Twenty-five kilobytes of unrelated documentation leaves the fix working; seven kilobytes of their own routing docs destroys it.

What is measured

Three libraries, each with one task an AI assistant reliably gets wrong, and each with a sentence in its own documentation that names the fix. Ten trials per cell. The only thing that changes is how that sentence reaches the model.

The one thing that holds across all three: the sentence works. These are not corrections written for the experiment — every one is quoted verbatim from the library's own documentation. The model reads the instruction and follows it.

It is not length. It is how much related material surrounds it.

The obvious reading of the table above is that long documents bury a correction — React Router's sentence sits at line 182 of a 213-line file, and there it never works. That was tested directly and it is wrong.

On Next.js: same task, same sentence, nothing varying but the amount of surrounding text and where the sentence sat in it. The padding was real Next.js documentation for unrelated APIs, checked never to state the signature under test.

Read the two middle rows together. Twenty-five kilobytes of schema-validation documentation leaves the correction working. Seven kilobytes of the library's own routing documentation destroys it — and it is the same sentence, from the same file, in both cases.

So it is neither length nor topic on its own. 25 KB of unrelated text is harmless. 215 bytes of the library's own routing text is harmless. About 7 KB of it is not. What crowds out a correction is the quantity of material about the same domain — and the other four files in React Router's pack turned out to be irrelevant. Its own containing file is enough.

That also explains Next.js, which looked like a counterexample. Its 6.6 KB page is the same domain as the correction but is entirely about the failing API — there is nothing in it competing for the same decision, so nothing to crowd anything out.

A confound worth stating

The three failures are not equally hard to correct. Next.js's is an arity error — "the second argument is required" is about as direct as a fix gets. React Router's is a field rename inside a destructured argument. It is entirely possible that some corrections are robust to their surroundings and others are fragile, and that this explains the table above better than anything about the documents.

What can be said, and what cannot

Supported: a short, specific sentence naming a breaking change fixes the failure it names, on all three libraries measured, 9–10 times out of ten. It is worth shipping one.

Supported: two of these three libraries already contain that sentence somewhere in their own documentation, and it is not reaching the model there.

Supported: the cause is not length. It is how much same-domain material surrounds the correction — 25 KB of unrelated docs leaves it working, 7.3 KB of the library's own routing docs does not.

Not supported, and withdrawn: that document length alone is the cause. That was an earlier conclusion on this page; the size-and-position sweep did not reproduce it.

Sizes span 2,217 characters to 5,673,960 under two filenames that promise the same thing. A model with no ability to fetch gets nothing usable from a link index, and nothing at all from a five-megabyte bundle. Next.js is worth copying on one point regardless of the above: it serves a Markdown version alongside every docs page — 6.6 KB where the HTML is 490 KB — and that file fixed its failure ten times out of ten.

Limits

One model (Claude Opus 5), three libraries, one failing task each, ten trials per cell, one-shot prompts rather than an agent that can search. The single-sentence arm is close to handing the model the answer — its entire context is the correction — so it measures whether a salient instruction is followed, not whether documentation works in normal use.
