The gap

2 things the agent gets wrong

Both are real code the model generated, verified by the TypeScript compiler against Prisma 7's actual types — and both are the same root cause: Prisma 7 now requires a driver adapter, and the model still writes the pre-adapter setup.

✗Constructing the clientTS2345
Agent wrote (Prisma 6)
const prisma = new PrismaClient({
  log: ["warn", "error"],
})
Prisma 7
import { PrismaPg } from "@prisma/adapter-pg"

const adapter = new PrismaPg({
  connectionString: process.env.DATABASE_URL,
})
const prisma = new PrismaClient({
  adapter,
  log: ["warn", "error"],
})
error TS2345: Argument of type '{ log: ("warn" | "error")[]; }' is not assignable to parameter of type 'Subset<PrismaClientOptions, PrismaClientOptions>'.
Why: Prisma 7 dropped the bundled query engine — the constructor now requires a driver adapter. The model passes v6-style options (log) but omits the now-required adapter, so the whole options object fails to type-check.
✗Setting the datasource URLTS2353
Agent wrote (Prisma 5–6)
new PrismaClient({
  datasourceUrl: process.env.DATABASE_URL,
})
Prisma 7
// the URL now flows through the adapter
const adapter = new PrismaPg({
  connectionString: process.env.DATABASE_URL,
})
new PrismaClient({ adapter })
error TS2353: Object literal may only specify known properties, and 'datasourceUrl' does not exist in type 'Subset<PrismaClientOptions, PrismaClientOptions>'.
Why: the datasourceUrl option (Prisma 5–6) was removed. In Prisma 7 the connection string is configured on the driver adapter instead.

What would move this number

Four changes, each one derived from a measurement above

Not general advice about writing good documentation. Every item below is something this run measured, and every one of them is checkable against Prisma's own shipped files.

1. constructor.md never mentions datasourceUrl.

The failing task writes new PrismaClient({ datasourceUrl }), a field v7 removed. It is fixed only in the arm that includes prisma-postgres-setup/references/prisma7-client.md — the only file in the set that names datasourceUrl at all. The pack an agent routes to for client construction, prisma-client-api, mentions it zero times.

So the fix arrived from a file about Postgres setup, which an agent working on client construction has no reason to load. Moving the removed-field list into constructor.md would put the answer where the question gets asked.

2. The file agents reach for hedges; the file they don't reach for is direct.

constructor.md heads the field adapter (Required for the SQL provider workflow) — a condition the reader has to decide applies to them. prisma7-client.md instead says: "Adapter is mandatory: new PrismaClient() with no arguments throws."

Same requirement, two registers, and the unambiguous one is in the file an agent is least likely to load. Stating the failure rather than the condition costs one sentence.

3. And the strongest one: make it shorter.

The adapter sentence, on its own, fixes bare new PrismaClient() 10 times out of 10. The same sentence inside your 25 KB pack fixes it 5 times out of 10. Nothing about the wording changed — only how much surrounded it.

So the failure is not comprehension and not refusal — the model follows the instruction when it reaches it. React Router shows the same pattern more starkly: 9 of 10 from a single sentence, 0 of 10 from that sentence inside its own 25 KB pack.

Length is the obvious culprit and it is not supported. A controlled sweep on Next.js put the same sentence at the end of 25 KB of unrelated docs and it still passed 10 of 10 — details here. Ship the short file, because that provably works. The reason the full pack does not is still an open question.

4. Worth saying plainly: the docs themselves are unusually good.

Across nine libraries surveyed, Prisma's llms-full.txt is one of only three files a model can use without fetching anything — 6,915 characters of prose, no link index. The comparable file from another library on this board is 5.7 MB. This is a routing problem, not a writing problem.

Why this matters

The version-drift gap

Models are trained on a snapshot of the past. The moment your SDK ships a breaking major, coding agents keep writing the old API — confidently, and it looks right — until they're retrained. For your users, that's broken code on their first try with your latest version.

The gap refreshes twice over: every new SDK major re-opens it, and every new model release shifts it. That makes it a moving target worth monitoring, not a one-time audit — which is exactly what SDKProof watches.

No opinions — just the compiler

How this was measured

15 realistic Prisma tasks → generated by claude-opus-5 → each solution written into a project with the real installed @prisma/client v7.8.0 and type-checked with tsc --noEmit.
A task passes only if it compiles clean. Failures are the compiler's own diagnostics (TS2554 / TS2353 / TS2339) — no LLM judge, no hand-waving. Reproducible: pinned package version, pinned model.
Scope — measured with no project context. The model gets the task and the package's type definitions, nothing else: no AGENTS.md, no editor rules, no agent skills. That is the point — it measures what a model reaches for unaided.

It matters here. From v7.9, prisma init installs agent skills that address these misses. Scored with them, on all 15 tasks and 3 trials: 87 → 93. The full breakdown is above; the short version is that their docs fix one of the two failures and the pack named after the task fixes neither. One-shot injection, not a full agent loop.

So read 87 as the floor — what an unconfigured agent produces — not as what a properly set-up Prisma project produces. Scored against @prisma/client 7.8.0, which predates those skills.
